repository anatomy / 2026-08-17 / commit 63114dd

Mabatakiは、顔認識ライブラリそのものではありません。入力された数値パラメータを、 作者が用意したKey Poseに従って2D Meshの頂点へ変換する、小さなWeb-first Runtimeです。 この文書は「どのファイルが何を担当し、1フレームがどう処理されるか」をコードに沿って説明します。

何を解決するリポジトリか

一般的なAuto Rigは、画像から「顔」「目」「髪」などを推測します。この推測は人型では便利でも、 人外キャラクターや独特な絵柄では品質が不安定です。Mabatakiは自動推測をCoreから外し、 作者が決めた形をRuntimeが忠実に補間する方式を選んでいます。

作者が決めるもの

画像のPart分け、Mesh、ParameterごとのKey Pose、必要ならSpringの頂点Weight。

Runtimeが保証するもの

値域のClamp、Keyframe補間、複数Bindingの加算、Spring計算、再利用可能な頂点バッファ。

したがって中心APIは、カメラではなく次の3行です。スライダー、録画データ、別Trackerのどれでも、 同じParameter値を作れば同じモデルを動かせます。 

const runtime = new MabatakiRuntime(model)
runtime.update({ mouthOpen: 0.72, headYaw: -0.2 })
const positions = runtime.getPartVertices('mouth')

この方針の根拠は ADR-0001、 ADR-0003、 ADR-0015 に記録されています。

Workspaceと依存方向

pnpm Workspaceは、責務をディレクトリ規約ではなくpackage境界として固定します。 依存は外側からCoreへ向かい、CoreからTrackerやRendererへ戻りません。

場所責務公開状態
packages/coreモデル検証、変形、Parameter、Spring、Smoothing公開可能
packages/mediapipeFace Landmarker、較正、配置、Accessory anchorprivate
packages/pixiFloat32ArrayをPixiJS Meshへ反映private
packages/webCanvas映像とマイク音声をMediaStream化private
apps/demo全packageを組み合わせる実験場非公開

ここでいう「依存ゼロ」はnpm package dependencyがゼロという意味です。 Coreの loadModel() はブラウザの fetch を使うため、 あらゆるJavaScript環境から完全に独立しているわけではありません。 すでに読み込んだJSONへ validateModel() を使う経路なら、画像APIやCanvasは不要です。

Core Runtimeの処理

Coreの中心は MabatakiRuntimeです。 Constructorはモデルを検証し、Partごとに基準頂点、出力頂点、Spring状態を一度だけ確保します。 以後は同じ Float32Array を再利用します。

1. Parameterを安全な範囲へ入れる

ParameterStoreは、 モデルが宣言したIDだけを保持し、値を min..max へClampします。 MabatakiRuntime.update()は未知IDを無視するため、 MediaPipeがモデル未対応の値を含んでいても、そのまま入力できます。

2. Keyframe列を区分線形補間する

accumulateBinding()はParameter値を挟む2個のKeyframeを探し、 それぞれの頂点deltaを線形補間します。範囲外の値は端のKeyframeへ固定されます。 Partに複数Bindingがあれば、結果は加算されます。

頂点 $i$ の最終位置は、概念的には次の式です。

$$ \boldsymbol{p}_i = \boldsymbol{b}_i + \sum_{k \in B}\mathtt{lerp}\!\left(\boldsymbol{d}_{k,\mathrm{lo},i}, \boldsymbol{d}_{k,\mathrm{hi},i}, t_k\right) + \boldsymbol{s}_i $$

記号意味
$\boldsymbol{p}_i$描画する最終頂点位置
$\boldsymbol{b}_i$モデルに保存された基準頂点
$\boldsymbol{d}$作者がKey Poseで編集した頂点差分
$\boldsymbol{s}_i$任意のSpringによる遅れ

3. SpringはKey Poseとは別に時間を進める

springBindingsは、髪や耳の先端を遅らせる仕組みです。 各頂点の weights が0なら接着点、1なら最大影響になります。 step()は最大1/120秒の小刻みな区間で減衰振動を計算し、 長時間停止後の復帰は250msへ制限します。現在のサンプルモデルにはSpring設定がありませんが、 Runtimeと検証は実装済みです。

4. dirtyフラグで不要な計算を避ける

Parameter更新またはSpring更新があったときだけ dirty = true になります。 描画が60fps、Trackingが30fpsでも、値が変化しない描画フレームではMesh変形を再計算しません。 返却バッファも再利用するため、毎フレームの配列生成を避けています。

model.jsonの読み方

モデル形式はプレーンJSONと画像ファイルです。 validateModel()が、Parameterの重複、頂点とUVの長さ、 Triangle index、Keyframe順序、delta数、Spring weightなどを読み込み時に検証します。 

{
  "version": 1,
  "parameters": [
    { "id": "mouthOpen", "min": 0, "max": 1, "default": 0 }
  ],
  "parts": [
    {
      "id": "mouth",
      "texture": "mouth.png",
      "mesh": {
        "vertices": [180, 105, 199.625, 105],
        "uvs": [0.4466, 0.2210, 0.4953, 0.2210],
        "indices": [0, 1, 9]
      },
      "bindings": [
        {
          "parameterId": "mouthOpen",
          "keyframes": [
            { "value": 0, "deltas": [] },
            { "value": 1, "deltas": [] }
          ]
        }
      ]
    }
  ]
}

上の deltas は説明用に省略しています。実データでは vertices と同じ要素数が必須です。座標は画像全体のPixel空間、 UVは0から1のTexture座標です。そのため顔が画像中央にある必要はなく、 尻尾や余白を含む画像でも、Mesh頂点とUVが正しければCoreは同じように処理します。

カメラから描画まで

MediaPipe Adapterは、Tracker固有値をRuntimeへ直接漏らしません。 face-tracker.tsが ランドマークとBlendshapeを、共通Parameterと画面配置情報の2系統へ変換します。

Parameter系統

Yawは鼻1番と輪郭234・454番の相対位置、Rollは左右輪郭を結ぶ線の角度から求めます。 口と目はMediaPipe BlendshapeをDead Zone、Full Scale、Gammaで較正します。 カメラ映像は鏡像なのでYawとRollの符号、左右Blinkの対応も反転します。 その後、呼び出し側が ExponentialSmoother を適用します。

View Transform系統

顔の画面位置、幅、回転はモデルの表情ではありません。 この値はRuntimeへ渡さず、PixiJSのRoot Containerへ適用します。 顔へ近づいたとき、顔・目・口・メガネをまとめて拡縮できるのはこの分離のおかげです。

汎用性についての重要な境界

Coreは画像内の顔位置を仮定しません。一方、 Camera Compositorは現状のサンプルを顔へ重ねるため、 MODEL_HEAD_X = 284.5、MODEL_HEAD_Y = 253.3、 MODEL_FACE_WIDTH = 455というモデル固有定数を持ちます。 任意モデルをCamera Overlayへ載せるには、これらをモデルmetadataまたはEditor出力へ移す必要があります。

PixiJSとWebRTC

PixiAvatarRendererは各Partに MeshGeometryを作り、毎フレーム aPosition bufferだけを書き換えます。 @mabataki/webはCanvasを captureStream()し、マイクのAudio Trackと結合します。 Signaling、Room、接続管理はLiveKitなど製品側の責務です。 

const video = captureCanvasStream(pixiApp.canvas, 30)
const outgoing = combineWithAudio(video, microphoneStream)

3つのデモの違い

Editor

apps/demo/src/main.ts

Part、Parameter、Key Poseを選び、頂点deltaを編集してmodel.jsonを書き出す制作PoC。

Viewer

apps/demo/src/viewer.ts

モデル固有ロジックを持たず、JSON、Texture、Runtime、Rendererを結ぶ最小の再生例。

Camera

apps/demo/src/camera.ts

Camera映像、Avatar、Accessory、任意の背景画像をレイヤー合成する統合PoC。

EditorがRenderer packageを直接使わない理由

EditorのEdit Modeは、通常のRuntime出力ではなく「選択中Key Poseのdeltaだけ」を生で表示します。 Preview Modeでは MabatakiRuntime を使いますが、編集ハンドルや選択領域を重ねるため、 Editor自身がPixiJS Meshを管理しています。これは重複というより、制作画面だけに必要な別経路です。

おすすめのコード読解順

ファイル数より因果関係を優先すると、次の順番が最短です。

  1. model.ts
    データ契約と不正入力の境界を把握する。まずinterface、次に validateModel() を読む。
  2. deform.ts
    59行だけで、Mabatakiの中心数学を確認する。accumulateBinding() が最重要。
  3. runtime.ts
    Parameter、buffer再利用、dirty判定、Springをどう束ねるかを見る。
  4. 実際のmodel.json
    1個の face Meshで、頭、口、左右の目を局所的に動かすBindingを照合する。
  5. PixiAvatarRenderer
    CoreのFloat32ArrayがGPUの頂点bufferになる接点を確認する。
  6. face-tracker.ts
    Tracker固有値をParameterとView Transformへ分ける理由を確認する。
  7. viewer.ts、 camera.ts、 main.ts
    最小再生、Camera統合、Authoringの順で外側を読む。

  • model.jsonの構造検証
  • 2点以上のKeyframe列補間
  • 複数Parameterのdelta加算
  • 任意の頂点Weightを使うSpring
  • PixiJSによる複数Part描画

  • 汎用的なPivot・Anchor metadata
  • 階層TransformとAttachment
  • Clip Maskと自然なまぶた遮蔽

  • AIによるMesh・Key Pose自動生成
  • WebRTC Signalingと通話Room
  • 複数Avatarとbundle sizeのBenchmark

現在の設計で最も重要なのは、Runtimeの成功とAuthoring自動化の成功を分離していることです。 将来AIがMeshやKey Poseを作るようになっても、出力が同じmodel.json契約ならCoreは変更されません。 逆にAuthoringが手動のままでも、Runtime、Renderer、Camera Adapter、通話組み込みは独立して利用できます。
